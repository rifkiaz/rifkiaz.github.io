    apa itu seal, token, policy, dan lease?
    • Seal dan unseal. Semua data Vault di storage dienkripsi. Kunci enkripsinya dikunci lagi pakai root key yang dipecah jadi beberapa unseal key (Shamir's Secret Sharing). Setelah restart, Vault selalu tersegel dan baru bisa dipakai setelah cukup banyak pemegang key memasukkan bagiannya, misalnya 3 dari 5.
    • Token. Semua permintaan ke Vault pakai token. Root token boleh apa saja, jadi di produksi cuma dipakai buat setup awal. Aplikasi dan orang dapat token lewat auth method seperti AppRole, userpass, atau Kubernetes.
    • Policy. Token cuma boleh melakukan yang diizinkan policy-nya, per path dan per kemampuan (read, create, update, delete, list, sudo). Yang ga disebut berarti ditolak. Di KV v2, path API-nya pakai prefix data/, jadi secret/app/db di CLI dicek sebagai secret/data/app/db.
    • Secrets engine. KV menyimpan secret statis (v2 punya riwayat versi). Database membuat user database baru tiap kali diminta. Transit mengenkripsi data tanpa menyimpannya, jadi aplikasi ga perlu pegang kunci.
    • Lease. Secret dinamis punya masa berlaku. Setelah lease habis atau dicabut (vault lease revoke), Vault menghapus user database-nya. Kredensial yang bocor jadi cuma berguna sebentar.
    • Seal darurat. Kalau ada insiden, vault operator seal langsung menghentikan semua akses. Data tetap aman di storage, tapi butuh unseal key lagi buat membukanya.

    Ini simulasi, bukan Vault beneran. Server, database, key, dan token-nya bohongan, IP-nya pakai rentang contoh, dan perintahnya cuma sebagian. Di produksi, Vault wajib pakai TLS (https). Semua cuma ada di browser kamu dan ga disimpan di mana pun.
